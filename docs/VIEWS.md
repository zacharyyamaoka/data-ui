# data-ui views: one dataset, one .base file, many views

> Generated by `docs/views/build.py` from `docs/views/views_data.py` and `docs/views/measurements.json` on 2026-10-25. Edit those, then rebuild; this file is the build spec for every view. The report with the live demo: `reports/data-ui-views-2026-10-25.html`.

**Seventeen views read one row model and one .base file. Ten sit on four stock engines: TanStack (table, pivot, list, cards, tree, compare, raw source), Vega-Lite (every chart), Pragmatic drag and drop (kanban) and React Flow (graph, Zach's call). Four take one library each: PhotoSwipe, Event Calendar, vis-timeline, MapLibre. KPI cards are the survey's kit as the SPEC names it. Pivot, record, form and compare have no stock part worth taking, so they are thin layers of ours, ~540 lines between them.**

## 2. Where this disagrees with the table lane, the survey or the SPEC

- **Chart engine: the survey said ECharts; the SPEC and this table say Vega-Lite.** The survey's default for shared charts was ECharts 6, largely because its KPI kit extracts Vibe Tracks' ECharts history chart.[5](obsidian://open?vault=zach_brain&file=Projects%2FBAM%20Robotics%2FNotes%2FReusable%20Components%20Across%20Zach%27s%20Apps%20(2026-10-25)) The SPEC picks Vega-Lite for every data-ui chart and keeps ECharts only inside Vibe Tracks' fixed drill-down;[6](file://~/data-ui/docs/SPEC.md) this table agrees on its own scores (Vega-Lite 89, ECharts 80). One consequence for the survey's kit 1: no `<bam-kpi-history>` on ECharts; the KPI card's sparkline is SVG and a full history is a `chart` view, so a page never loads two chart engines (216 + 283 KB gzipped).
- **The row model has to come out of the table renderer.** In the lane, filter → pivot → search → TanStack all run inside the table element (`_compute()` in views.js).[4](file://~/robotparts/.claude/worktrees/lane-tables/design/tables-2026-10-25/views/src/) For every layout to read the same rows, that pipeline becomes the core of `<data-views>` and the table becomes one registered layout among the rest. It is a move of ~110 lines (the demo's core.mjs is that move), best done inside the SPEC's barrier step, which moves views/ into this repo anyway.[6](file://~/data-ui/docs/SPEC.md)
- **Cards: virtualised, not plain CSS grid.** The SPEC draws `cards` with CSS grid.[6](file://~/data-ui/docs/SPEC.md) At 1,149 cards that is 1,149 nodes; TanStack Virtual's `lanes` (already in the bundle, 0 KB) kept 28 in the DOM in the demo and give masonry later. Same keys, same look.
- **Graphic Walker: two facts differ from the SPEC (§8.9); the decision does not.** Its package does ship a non-React entry, `embedGraphicWalker(dom, props)` in dist/vanilla.d.ts, but it bundles React, so robotparts would still pay for it. Its natural-language box posts to api.kanaries.net by default, but `askviz` and `vlChat` accept your own function, so Zach's own agent could answer it.[28](https://github.com/Kanaries/graphic-walker) Still a second grammar beside the `.base` file: not adopted, as the SPEC says.
- **Types and keys beyond the SPEC.** The SPEC's seven layouts are the core.[6](file://~/data-ui/docs/SPEC.md) This table adds `calendar`, `timeline`, `graph`, `record` and `compare`, and the keys `tree`, `lightbox`/`media`/`caption`, `start`/`end`/`calendarView`, `edges`/`layout`, `edit` and `compare`. The schema already accepts them (it allows extra keys);[7](file://~/data-ui/schemas/view.schema.json) the checker should learn each one when its view is built, so the grammar stays one grammar.
- **`kanban`, not `board`.** The brief said `board`; Obsidian 1.14 ships the layout as `kanban`, with `groupBy`, `groupOrder` and `columnWidth`.[8](file://~/.config/obsidian/obsidian-1.14.5.asar),[13](https://obsidian.md/changelog) This table and the SPEC both use `kanban`.[7](file://~/data-ui/schemas/view.schema.json)
- **Found while building: A unit bug in the table lane's actuator rows.** design/tables-2026-10-25/build_prototypes.py multiplies every actuator mass by 1,000, assuming kilograms (ACT_COLUMNS, line 127). One record's canonical mass is the spec `mass` in grams: CubeMars AKE40-6 KV90, the level-2 part, robotparts says 140 g and the table and this demo show 140,000 g. The Ashby chart showed it at once (the lone dot at 140 kg). The fix is the spec's own unit, not a factor; not fixed here, since that file belongs to the lane.[3](file://~/robotparts/.claude/worktrees/lane-tables/design/tables-2026-10-25/build_prototypes.py)

## 3. The criteria

Weights come from the brief's constraints: stock first, permissive licences, framework-free or an island, the shared row model, agent-editable config, CSS-variable theming, size. Scores are 1-5; the total is weighted to 100. `Stock and maintained`, `Licence` and `Size` are computed from npm and the measurement (§6) unless a row says otherwise; the rest are judgement, explained in each row's note.

| Criterion | Weight | What a 5 means |
|---|---|---|
| Does the view's job | 20 | covers every behaviour in the view's "what it shows" (a gap we fill in under 100 lines 4; part of the job 2-3; a helper only 1) |
| Stock and maintained | 15 | the lower of stock share (the library does the view, under 50 lines of ours 5; under 150 lines 4; the engine is stock but the surface ours 3; all ours 2) and release age (auto from npm: ≤6 months 5, ≤12 4, ≤24 3, ≤36 2, older or archived 1) |
| Licence | 10 | MIT / BSD / Apache / ISC with nothing we need behind a paid tier (open-core where we would hit the paywall 2-3; GPL, commercial or proprietary 1) |
| Framework-free or island-able | 15 | plain ESM, no framework runtime (a framework compiled inside 4; a React island 2-3; needs a React app 1) |
| Reads the shared row model | 10 | takes our filtered rows as they are (a thin mapping 4; keeps its own data store we sync 3; owns data and query 2) |
| Agent-editable config | 15 | the whole view is declarative JSON an agent writes into the .base entry (a small option object we map 4; callbacks needed 3; JS calls or its own verbose spec 2) |
| CSS-variable theming | 5 | ships CSS custom properties, or is headless so our CSS draws it (a theme object we fill from resolved tokens 3; class-based CSS only 2) |
| Size (min+gz, lazy per view) | 10 | auto from the measured bundle: ≤15 KB 5, ≤50 4, ≤120 3, ≤300 2, more 1; already in the shared bundle 5 |

## 4. The view-plugin contract

**Register** (the model is Obsidian's own Bases view API):

```js
import { registerView } from 'data-ui';

registerView('chart', {                       // Obsidian: plugin.registerBasesView('chart', {...})
  name: 'Chart',                              //   BasesViewRegistration.name
  icon: 'chart-scatter',                      //   BasesViewRegistration.icon (lucide)
  load: () => import('./views/chart.js'),     //   .factory, made lazy: the library loads when the view opens
  options: (view) => [                        //   .options: the view's settings menu, same option types
    { type: 'property', key: 'x', displayName: 'X axis' },
    { type: 'dropdown', key: 'scale', options: { linear: 'Linear', log: 'Log' } },
  ],
});

// views/chart.js
export default class ChartView {              // Obsidian: class extends BasesView
  constructor(host, el) {}                    //   factory(controller, containerEl)
  update({ rows, groups, columns, view, tokens, total }) {}   //   onDataUpdated(), reading this.data / this.config
  destroy() {}                                //   Component.onunload()
}
```

**What a plugin receives** in `update()`:

- `rows`: the view's rows after the file's and the view's `filters`, in `sort` order: the same objects, in the same order, as the table draws (TanStack's row model, `.original`)
- `groups`: `[{key, rows}]` in `groupOrder` when the view has `groupBy` (named groups with no rows still appear), else `null`
- `columns`: the dataset's property schema: `{id: {label, type, unitText, decimals, labels, derived, better}}`
- `view`: a frozen copy of this view's `.base` entry: Bases keys plus data-ui keys
- `tokens`: the SPEC's `--data-*` tokens resolved to colours (`bg, fg, muted, border, accent, series[], font`, and `css`: every `--data-*` token by name), sent again on a theme change, because canvas and SVG libraries cannot read `var()`.[6](file://~/data-ui/docs/SPEC.md) A view entry may write a colour as `var(--data-series-3)`; the plugin resolves it from `tokens.css`
- `total`: the dataset's row count, for "N of M"

**What it may write back:** only these three calls.

- `host.setView(patch)`: merge keys into this view's entry. The host validates it against `schemas/view.schema.json` and writes the `.base` file (or the URL and local presets on a static site). Obsidian's equivalent is `this.config.set(key, value)`; its map view writes `center` and `defaultZoom` this way.[14](https://github.com/obsidianmd/obsidian-maps)
- `host.propose({id, set})`: ask for a data edit; resolves `{ok, reason}`. The host decides: derived or read-only properties refuse, a writable host applies and re-emits the rows. Obsidian's board does the same through `fileManager.processFrontMatter` in a transaction.[8](file://~/.config/obsidian/obsidian-1.14.5.asar),[15](obsidian://open?vault=zach_brain&file=Projects%2FObsidian%20Vibe%20Kanban%2FResearch%20-%20Bases%20Kanban%20prior%20art)
- `host.open(id)`: open the shared record peek.

A plugin never mutates rows, never fetches data, never writes outside its own view entry, and never loads code or tiles from another origin.

**How `type:` selects it.** `views[i].type` picks the plugin from the registry. data-ui uses Bases' own names where Bases has the view (`table`, `cards`, `list`, `kanban`, `map`: all five read from Obsidian 1.14.5 and the Maps plugin) and adds `pivot`, `chart`, `kpi`, `calendar`, `timeline`, `graph`, `record` and `compare`.[8](file://~/.config/obsidian/obsidian-1.14.5.asar),[14](https://github.com/obsidianmd/obsidian-maps),[7](file://~/data-ui/schemas/view.schema.json) Obsidian keeps view keys it does not know, so a data-ui file stays a valid `.base` file; what Obsidian shows for a type it lacks is UNVERIFIED. An unknown type in data-ui draws the table with a one-line notice.

**Is Bases' plugin API a model to copy?** Copy it, closely. Obsidian's API is the same shape: `registerBasesView(id, {name, icon, factory, options})`; a `BasesView` gets the already filtered, sorted and grouped result as `this.data` (`data` and `groupedData`) and its own entry as `this.config` with `get` and `set`; `onDataUpdated()` runs on every data or config change; the settings menu is declared as options (`dropdown`, `property`, `slider`, `text`, `toggle`, `multitext`, …).[9](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts),[10](https://github.com/obsidianmd/obsidian-developer-docs/pull/203),[15](obsidian://open?vault=zach_brain&file=Projects%2FObsidian%20Vibe%20Kanban%2FResearch%20-%20Bases%20Kanban%20prior%20art) data-ui changes three things: `load()` is lazy (a page should not pay 283 KB for a chart it never opens); data edits are explicit proposals instead of direct frontmatter writes; and `tokens` arrive resolved, because charts and maps draw on canvas.

**A React island inside a framework-free page** (the graph view, and any React-only part later): the plugin's `load()` imports `react`, `react-dom/client` and `@xyflow/react` together; the constructor calls `createRoot(el)`; `update()` calls `root.render(<Flow nodes edges />)` with nodes and edges built from `rows`; `destroy()` calls `root.unmount()`. React 19 renders into any element, including a shadow root, and handles custom elements natively.[50](https://react.dev/blog/2024/12/05/react-19) The page pays React once, only when a graph opens: measured 127.6 KB gzipped for React 19.3.1 + react-dom/client + @xyflow/react 12.12.0, + 3.0 KB of CSS and 16.6 KB for dagre. In Clank, where React is already loaded, the same view costs 60.7 + 16.6 KB.[20](file://~/data-ui/docs/views/measure.py) In a shadow root, React Flow's stylesheet goes into `adoptedStyleSheets`.

### List · `type: list` · later

One line per row: the title, then properties inline (bullets, numbers or none), under group headings. The phone layout of a table.

- **Use cases:** robotparts catalog: search results and every table at phone width; Vibe Tracks KPIs + runs: the runs feed; ML experiment tracking: recent runs; Money: recent transactions

## 6. How the numbers were made

- **Sizes:** `docs/views/measure.py` installs every candidate at the version in `measurements.json` (npm `--ignore-scripts`), bundles its documented entry with esbuild 0.25.12 (minified, ESM, browser), React external, and gzips at level 9. CSS is the shipped stylesheet, with its count of custom-property definitions as the theming evidence. Cross-check: Tabulator measures 103.4 KB, the table lane measured 104.
- **The demo:** 1,149 actuators from the table lane's `site/data/actuators.json` (robotparts release 2026.10.25); its bundles are 35 KB gzipped (core, cards, board, TanStack, Pragmatic) and 284 KB (the chart plugin with vega, vega-lite, vega-embed), the second loaded only when the chart tab opens.
- **Bases facts:** read from Obsidian 1.14.5's own app.js (view ids and option keys) and the Maps plugin's source, not from memory.

## 7. Perspective: the whole-suite contrast

Perspective 5.6.1 (now `@perspective-dev/*`, Apache-2.0) is the one stock suite closest to "one dataset, many views": one JSON viewer config switches a datagrid, a pivot (group_by, split_by), d3fc charts and a map over the same table.[51](https://github.com/finos/perspective),[19](https://registry.npmjs.org/) It is not the base because its engine is 4.27 MB of WebAssembly that gzip cannot shrink, it runs in a module worker, Zach found its UI "super technical", its chart plugin lags (4.4.1, April) and it has no cards, board, calendar, timeline or graph.[2](file://~/robotparts/reports/robotparts-tables-2026-10-25.html) It stays the candidate engine for a million-row dataset, behind the same row-model seam. AG Grid with AG Charts is the other suite and fails on licence: grouping, pivot, tree data and integrated charts are Enterprise ($999 / $499 / $1,498 per developer).[46](https://www.ag-grid.com/license-pricing/)

## 8. Left out on purpose

- Writes to robotparts or any other repo: nothing outside ~/data-ui changed. SPEC.md and its report are the other agent's and untouched.
- Building the views beyond the three in the demo; the next build does that from this file.
- Bundle sizes of AG Grid, DataTables, WebDataRocks, Flexmonster, Bryntum, masonic, Clusterize, jsdiff and Web Awesome's drawer (n/m in the tables): each fails a gate before size matters, or is a helper.
- Svelte Flow's size: it needs a Svelte compile step, which this measurement does not have.
- A11y beyond the basics: keyboard moves on the board, focus order in the peek. The build must add them.
- Treemap, sunburst, Sankey and parallel coordinates: later chart presets, not views.
